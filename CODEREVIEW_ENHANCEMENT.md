## P1 — High

### [R-001] Bound unauthenticated readiness write probes

- **Type:** Review finding
- **Priority rationale:** This can become an externally triggerable availability problem when the service is bound beyond loopback or placed behind a reverse proxy. It is not P0 because the default Compose binding is `127.0.0.1`, the probe is small, and the application remains bounded by request/database timeouts; it is higher than P2 because the application itself does not enforce that deployment boundary.
- **Location:** `internal/web/core.go:615,620,1217-1233`; `internal/store/schema.go:34-36,72-77,604-635`; `compose.yaml:8,36-40`; `README.md:158-161`
- **Evidence:**
  - The router applies a 90-second request timeout and registers `/readyz` without authentication or a route limiter (`internal/web/core.go:615-620`). The handler calls `Store.Ready` for every request (`internal/web/core.go:1217-1233`).
  - `Store.Ready` performs a read health check followed by `Writable`. `Writable` starts a transaction, inserts into `application_logs`, reads the inserted row, and rolls the transaction back (`internal/store/schema.go:593-635`).
  - Production writes use a single database connection (`internal/store/schema.go:34-36`) with a five-second SQLite busy timeout (`internal/store/schema.go:72-77`). Concurrent readiness callers therefore queue at the same writer boundary as application and scheduler writes; there is no in-flight cap around the endpoint.
  - Compose probes the endpoint every 30 seconds and defaults the port to loopback (`compose.yaml:8,36-40`), but `LISTEN_ADDR`/proxy deployment can make all routes reachable from a network caller. The README intentionally documents `/readyz` as unauthenticated (`README.md:158-161`).
  - Existing tests cover a normal writable probe and a read-only failure (`internal/web/web_test.go:186-216`, `internal/store/edge_paths_test.go:628-640`), but do not establish a concurrent-request bound or prove that normal writes remain responsive during a probe burst.
- **Impact:** A caller able to reach the endpoint can turn an inexpensive-looking health URL into repeated writer transactions. A burst can consume the single writer connection, increase write wait time for sign-in, imports, scheduler state, and notifications, and leave many handler goroutines queued until their request deadlines. This can create a self-reinforcing health/restart incident even though the database is otherwise healthy.
- **Recommendation:** Keep the endpoint unauthenticated for container orchestration, but separate the public probe from an unbounded synchronous write. The smallest credible change is a single-flight or semaphore-protected writer-capability check with a strict probe deadline and a short-lived cached result; the read-only schema check can remain cheap and direct. Preserve the current fail-closed classification for read-only/full/unavailable databases. A background or periodic probe may update the cached writer state, while concurrent callers receive the last fresh result or a bounded failure rather than queuing indefinitely. A deployment-level loopback/proxy rule is useful defense in depth, not a substitute for the application bound.
- **Acceptance / validation:**
  - Add tests for writable, read-only, full, and unavailable states, plus a concurrent burst against `/readyz` while a normal write is pending.
  - Assert that at most the intended number of writer probes are active, that probe wait time is bounded below the healthcheck/request budget, and that ordinary writes are not starved by probe callers.
  - Run a local load test against the configured server and confirm bounded goroutine growth, writer wait metrics, and stable readiness behavior when the endpoint is reachable through the intended proxy topology.
- **Effort:** M
- **Confidence:** High
- **Trade-off / challenge:** Caching introduces a freshness interval: a database that becomes read-only between probes may remain reported healthy briefly. Direct probing gives fresher state but needs serialization and a hard deadline. The owner should choose the maximum acceptable stale-readiness window explicitly.

## P2 — Medium

### [E-001] Exercise disaster recovery in isolated CI

- **Type:** Enhancement
- **Priority rationale:** Backup/restore is a release-critical safety net for a forward-only migration system, but it currently has no automated execution gate. The cost is higher than a unit test, yet the consequence of discovering a broken restore only after an upgrade or data loss is materially higher.
- **Location:** `Makefile:54-61`; `scripts/backup.sh:1-96`; `scripts/restore-smoke.sh:1-183`; `.github/workflows/docker.yml:22-110`; operational contract documented at `README.md:1068-1115`
- **Evidence:**
  - The Makefile states that the 279 lines of disaster-recovery shell are executed by no gate and wires `backup-smoke` only as a local target because it stops the running app and manipulates the real data volume (`Makefile:54-61`).
  - The CI workflow runs the Docker test target, container startup/persistence smoke test, race/coverage/format/tooling/lint/vulnerability checks, and publication, but has no backup or restore job (`.github/workflows/docker.yml:22-110`).
  - `backup.sh` resolves the live Compose container and mounted `/data` volume, stops the service, streams a checksum-protected archive, writes a marker, and attempts restart. `restore-smoke.sh` verifies the sidecar, extracts into a disposable volume, runs SQLite integrity and foreign-key checks, starts an immutable image with the original encryption key, checks readiness, and compares durable state across restarts. Shell syntax checks cannot validate these Docker, volume, signal-cleanup, and restart interactions.
  - The README correctly tells operators to rehearse restores before replacing production data (`README.md:1095-1106`), which makes the missing automated rehearsal a delivery gap rather than an undocumented feature.
- **Impact:** A regression in volume discovery, archive/checksum handling, signal cleanup, image selection, encryption-key compatibility, SQLite integrity, or restart persistence can ship while all Go and container-startup tests remain green. Operators may have a backup artifact that cannot restore the application or preserve notification destinations when it is needed.
- **Recommendation:** Add a CI-only disaster-recovery job that runs both scripts against a disposable Compose project, named volume, container, and fixture database. Seed representative durable state, including at least one destination encrypted with a known test key; build or import the exact release image under an immutable digest; run `backup.sh`, then `restore-smoke.sh`; and assert archive/sidecar permissions, integrity/foreign-key checks, key-preserving startup, clean-stop status, restart fingerprint stability, and cleanup on success and interruption. Keep production-volume mutation opt-in. Run the rehearsal on release candidates as a blocking gate and on main/nightly as a recurring signal if runner time makes every pull request too expensive.
- **Acceptance / validation:**
  - CI invokes the actual repository scripts in an isolated project and fails when either script returns nonzero; no developer or shared production volume is touched.
  - The fixture proves encrypted destinations can be opened with the original key, a wrong key fails closed, the checksum sidecar is required by default, SQLite integrity/foreign-key checks pass, and durable state is unchanged after a stop/start cycle.
  - Failure-path tests cover SIGTERM/SIGHUP cleanup and confirm that temporary containers, volumes, and archive files do not leak. Document the job’s image-digest and fixture-key handling without using real credentials.
- **Effort:** L
- **Confidence:** High
- **Trade-off / challenge:** A release-blocking Docker job adds runner time and requires careful handling of image digests and disposable credentials. A scheduled-only job is cheaper but allows a broken recovery path to reach users. Decide which release classes require a hard gate and which only require an alert.
